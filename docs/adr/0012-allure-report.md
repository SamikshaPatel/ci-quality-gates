# ADR-0012: Every run publishes an Allure report next to its run report

**Status:** Accepted · 2026-11-05

## Context
The run report answers "what happened and who acts next" at the gate level. A developer fixing a failure needs the test level: which step failed, the request and response, a screenshot of the page, and whether the test has failed before. Test results servers (ReportPortal, Allure TestOps) do this for large teams; this project needs it free and without a server.

## Decision
- Every PR and nightly run builds an **Allure report** from the results all four gates wrote, and publishes it with the run on the history site, at `runs/<run>/allure/`. The run report and the history table link to it.
- **API tests** attach every request and response (`allure-rest-assured`). **UI tests** attach a full-page screenshot and the URL when they fail, taken before the page closes.
- **Categories** (ENV, CODE, flaky) are generated by the evaluator from the same `env_patterns` the gates use, so the report and the gate verdict can never disagree.
- **Trends** carry over between runs: each report starts from the previous report's history on `gh-pages`.
- The report is a single HTML file. Reports are kept for the newest 30 runs; older runs keep their run report and history entry.
- Building the report can never fail a gate: if Allure fails, the run warns and carries on.

## Consequences
- The run report stays the place to decide; Allure is the place to debug.
- `gh-pages` grows with every report. Pruning keeps the site small, but git history still grows; a periodic squash of `gh-pages` history would be the next step at scale.
- The report is static, so it can't be searched across runs; that is what the flakiness score (ADR-0013) and the Grafana dashboard are for.
